## 第 0 站：全局地图与运行方式



### 要回答的问题

- 这个项目分几层，每层负责什么？
- 程序从哪里开始执行，到哪里结束？
- 屏幕上看到的东西是谁创建的？



### 原理要点

本项目是**简化版 UE5 分层结构**。核心分层思想是：越底层越通用越稳定，依赖方向严格单向向下。`Core` 不知道 `Renderer` 的存在，`RHI` 不知道具体后端的存在。

一个必须先建立的概念：**应用层与引擎内核分离**。`Sandbox` 是应用，负责「场景里有什么」；`Engine` 是内核，负责「每帧按什么顺序做事」。两者通过回调注入连接，而不是 `Engine` 里硬编码场景内容。

```text
Sandbox（应用层，示例场景）
  └─ Engine（内核调度）
       ├─ World / Actor / Component      游戏侧状态
       ├─ RenderCore                     游戏侧与渲染侧的共享类型
       ├─ Renderer（FScene / SceneRenderer）渲染侧组织
       ├─ RHI 抽象 → OpenGL 或 Vulkan 后端（配置期二选一）
       ├─ Asset                          资源导入
       └─ Platform / Input / Core        基础设施
```

## 第 1 站：主循环与帧结构

**前置**：第 0 站

### 要回答的问题

- 一帧里到底发生了什么，按什么顺序？
- 为什么要区分 GameThread 和 RenderThread，即使现在是单线程？
- deltaTime 为什么要裁剪上限？



### 原理要点

**游戏引擎的本质是一个无限循环**：处理输入 → 更新状态 → 渲染 → 重复。难点不在于循环本身，而在于**阶段边界的划分**。

本项目的 `Engine::Tick` 划分为六个阶段：

```text
1. PumpPlatformMessages()    轮询窗口事件（键盘、鼠标、窗口大小）
2. TickInput(dt)             推进输入状态机
3. TickGameThread(dt)        应用逻辑 + World/Actor/Component 更新
4. SendAllEndOfFrameUpdates() 游戏侧 → 渲染侧的同步提交点   ★ 关键边界
5. TickRenderThread(dt)      BeginFrame → 构建视图 → 渲染 → EndFrame
6. EndFrame(dt)              清理输入过渡态、统计 FPS
```

**为什么阶段划分重要**：这些阶段名称借鉴 UE5，虽然当前全在一个线程上跑，但边界的位置决定了将来能否拆成两个线程。第 4 步是整个设计的枢纽——它是游戏侧状态流向渲染侧的唯一通道。只要所有同步都经过这里，将来把它换成「向命令队列 push」就能引入渲染线程，而不需要重写组件系统。

反例是让 `MeshComponent` 直接持有 GPU buffer 并在 `Tick` 里更新——这样的代码在单线程下能跑，但永远拆不出渲染线程。

**deltaTime 裁剪**：断点调试或窗口拖动时，两帧间隔可能是几秒。不裁剪的话，物理和动画会一步跳出天际。这是所有引擎的标准做法。

**Skipped 帧**：窗口最小化时 framebuffer 尺寸为零，无法渲染。此时后端返回 `RHIFrameStatus::Skipped`，Engine 睡眠 16 ms 避免空转烧 CPU。

## 第 2 站：数学与坐标约定 ★

**前置**：无

这一站优先级最高。图形学中至少一半的诡异 bug 来自约定不一致，而不是公式写错。

### 要回答的问题

- 本项目用的是左手系还是右手系？Y 轴朝哪？
- 矩阵是行主序还是列主序？`M * v` 还是 `v * M`？
- 为什么法线不能直接用 model 矩阵变换？
- NDC 深度范围是 `[0,1]` 还是 `[-1,1]`，谁决定？



### 原理要点

**约定不是对错问题，是一致性问题。** 每个引擎都可以自选，但一旦选定，从 CPU 数学库到 shader 到后端适配必须全程一致。混用两套约定的表现通常是「画面镜像」「上下颠倒」「法线朝反」「深度测试全过或全不过」。

本项目的约定：


| 项目     | 约定                                            | 备注                                          |
| ------ | --------------------------------------------- | ------------------------------------------- |
| 手性     | **右手系（RH）**                                   | `LookAtRH`、`PerspectiveRH_ZO`               |
| 轴向     | **Y 上，Z 前**                                   | `Vector3::Up = (0,1,0)`，`Forward = (0,0,1)` |
| 矩阵存储   | **列主序** `M[column][row]`                      | 与 glm 一致                                    |
| 向量变换   | `Matrix4 * Vector4`，**左乘**                    | 组合时父变换在左                                    |
| VP 组合  | `ViewProjection = Projection * View`          |                                             |
| TRS 组合 | `Translation * Rotation * Scale`              | 对点先缩放再旋转再平移                                 |
| NDC 深度 | `[0,1]`**（ZO）**                               | `GLM_FORCE_DEPTH_ZERO_TO_ONE`               |
| 欧拉角    | Yaw=Y，Pitch=X，Roll=Z，组合序 `yaw * pitch * roll` |                                             |
| 四元数    | `{X,Y,Z,W}`，W 为实部                             |                                             |


**一个必须注意的例外**：`Transform::GetForward()` 返回局部 +Z 方向，但**相机的观察方向是局部 -Z**。`CameraComponent::BuildViewInfo` 里写的是 `forward = (-GetForward())`。这个反直觉的约定来自 OpenGL 传统（相机看向 -Z），与 UE 和大多数教程一致。搞混的表现是相机永远背对场景。

**法线变换为什么要逆转置**：法线是垂直于表面的方向，不是普通向量。在非等比缩放下（比如 X 拉长 2 倍），表面倾斜了，但用同样的矩阵变换法线会得到错误的方向——法线会朝拉伸方向偏，不再垂直于表面。数学上，若切向量用 `M` 变换，要保持 `n·t = 0`，法线必须用 `(M⁻¹)ᵀ` 变换。本项目在 `Matrix4::GetNormalMatrix()` 中实现，每次 draw 通过 `ObjectBlock` 传给 shader。

**深度范围为什么会不一致**：OpenGL 传统 NDC 深度是 `[-1,1]`，D3D 和 Vulkan 是 `[0,1]`。本项目统一选 `[0,1]`，因为它精度更好且是现代 API 主流。OpenGL 4.5 通过 `glClipControl` 也能切到 `[0,1]`；若硬件不支持，`OpenGLDevice::AdjustProjectionMatrix` 会把矩阵重映射回 `[-1,1]`。这个「引擎统一约定 + 后端适配」的模式贯穿整个 RHI 设计。

**Frustum 剔除**：`Frustum::FromViewProjectionRH_ZO` 用 Gribb-Hartmann 方法，直接从 VP 矩阵的行组合出 6 个裁剪平面——因为裁剪条件 `-w ≤ x ≤ w` 展开后就是平面方程。AABB 测试用 P-vertex 优化：只需测试沿平面法线最远的那个角点，而非全部 8 个。

**随机数**：`Random.cpp` 用 PCG32 而非 `rand()`。整数区间用**拒绝采样**而非取模，因为取模会引入分布偏差（若区间不整除范围，小的值出现概率更高）。

## 第 3 站：平台窗口与输入

**前置**：第 1 站

### 要回答的问题

- C 风格的 GLFW 回调怎么调用 C++ 成员函数？
- 「按住」和「刚按下」在实现上有什么区别？
- 逻辑窗口尺寸和 framebuffer 尺寸为什么是两个值？



### 原理要点

**C 回调到 C++ 对象的桥接**：GLFW 是 C 库，回调是自由函数指针，无法直接绑定成员函数。标准解法是 `glfwSetWindowUserPointer(window, this)` 把对象指针存进窗口，静态回调里取回来再转调。这个模式在包装任何 C 库时都会用到。

本项目在这之上又加了一层：`GLFWWindow` 持有 `std::function` 成员，`InputManager` 注册 lambda 进去。这样 `Input` 模块完全不知道 GLFW 的存在。

**输入状态机的三阶段**：

```text
事件回调        →  写入 States 与 Just* 标记
Tick()          →  逻辑读取状态、计算鼠标 delta
PostTick()      →  清空所有 Just* 标记
```

「按住」是**持续状态**，「刚按下」是**单帧事件**。后者必须在帧末清空，否则会连续多帧触发。这就是第 1 站里 `EndFrame` 的作用。注意 `InputAction::Repeat`（长按重复）只维持 States 而不产生 JustPressed，否则长按会被误判为反复按下。

**逻辑尺寸 vs framebuffer 尺寸**：在 Retina / 高 DPI 屏幕上两者不同（比如逻辑 800×600 对应 framebuffer 1600×1200）。**渲染必须用 framebuffer 尺寸**，viewport 和投影 aspect 都基于它；UI 布局和鼠标坐标才用逻辑尺寸。搞混的表现是高 DPI 屏上只渲染画面左下角四分之一。

**FlyCameraController 的两个实现细节**值得注意：一是维护 yaw/pitch 标量状态而非累积四元数，避免浮点误差累积导致的滚转漂移，并且pitch 限幅 ±89° 防止越过天顶翻转；二 是切换到 `CursorMode::Disabled` 时 GLFW 会把光标 warp 到中心，产生一个巨大的假 delta，因此代码跳过前 2 帧的 delta。不处理的表现是每次按下右键视角瞬间乱甩。

## 第 4 站：内存系统 ○

**前置**：无，独立主题

### 要回答的问题

- 为什么游戏引擎不直接用 `malloc`？
- TLSF 凭什么能做到 O(1)？
- 有序停机（shutdown ordering）为什么是内存和日志系统的硬约束？



### 原理要点

**通用分配器的问题**：`malloc` 为通用场景优化，需处理任意大小、任意生命周期，且最坏情况延迟不可预测。游戏引擎需要稳定的帧时间，一次几毫秒的分配停顿就是掉帧。此外，引擎还需要知道内存花在哪里（渲染？资源？物理？），这是 `malloc` 给不了的。

**TLSF（Two-Level Segregated Fit）**：核心思想是用两级位图索引空闲块。第一级按 2 的幂划分大小类，第二级在每个大小类内再细分。查找合适空闲块时，用位运算（`ffs`/`clz` 这类指令）直接定位到非空的链表，因此是 O(1) 且最坏情况有界。这与传统的 first-fit / best-fit 需要遍历链表形成对比，是实时系统首选的分配算法。

本项目的封装层在 TLSF 之上加了：

- **多 Pool 扩容**：`tlsf_add_pool` 按需追加，16 MB 起按几何增长
- **用户 Header**：每次分配在返回指针前插入 `AllocHeader`（含 magic `'TEMM'`、对齐、tag、请求字节数），支持超对齐分配与按 tag 统计
- **MemoryTag 分类**：Core / RHI / Renderer 等分类统计，这是内存 profiling 的第一步

**全局 new/delete 默认未接管**：`GlobalNewDelete.cpp` 由 `TE_ENABLE_GLOBAL_NEW_DELETE` 控制且当前未启用。引擎内部走显式的 `TE::New` / `TE::Delete`，STL 容器通过 `TEngineAllocator` 接入。这是有意的取舍：全局 hook 覆盖面广但会影响第三方库和标准库内部分配，调试时难以区分来源。

注意 `MakeShared` 的对象走 TLSF，但 `shared_ptr` 控制块仍走系统 malloc。

**有序停机契约**：`MemoryShutdown()` 和 `Log::Shutdown()` 都要求「所有可能使用它的线程已经停止」。违反的表现是退出时崩溃或死锁——某个后台线程还在写日志，日志系统已经把队列销毁了。这类问题只在退出路径出现，容易被忽略但很难查。项目里已经踩过一次，见 [SimpleTest 内存 Shutdown 并发问题分析](../reference/临时问题分析-SimpleTest内存Shutdown并发.md)。

## 第 5 站：资源导入管线

**前置**：第 2 站

### 要回答的问题

- 一个 `.fbx` / `.obj` 文件怎么变成可渲染的数据？
- 什么是 Section，为什么一个模型要拆成多段？
- 切线是什么，为什么法线贴图需要它？



### 原理要点

**导入器的职责是「格式无关化」**：磁盘上有几十种模型格式，引擎内部只应有一种表示。Assimp 负责解析各种格式，导入器负责把结果转成引擎的 `StaticMesh`。

关键设计：**Assimp 头文件只出现在** `Private/AssetImporter.cpp`，公开接口完全不暴露。这样将来换掉 Assimp 不影响任何调用方。这是「第三方依赖私有化」的标准做法，`Core` 对 glm 和 spdlog 也是同样处理。

**后处理 flags 决定顶点属性是否可用**：


| Flag                              | 作用                  |
| --------------------------------- | ------------------- |
| `aiProcess_Triangulate`           | 把多边形拆成三角形，GPU 只认三角形 |
| `aiProcess_GenSmoothNormals`      | 缺法线时生成平滑法线          |
| `aiProcess_JoinIdenticalVertices` | 合并重复顶点，让索引缓冲有意义     |
| `aiProcess_CalcTangentSpace`      | 计算切线，**法线贴图的前提**    |


本项目**不使用** `aiProcess_FlipUVs`，因为引擎约定纹理原点在左上（与 Vulkan / D3D12 一致）。OpenGL 原点在左下，差异在 `OpenGLTexture` 上传时通过翻转行序处理。

**Section 是什么**：一个模型文件通常包含多个部分，各用不同材质（车身、玻璃、轮胎）。GPU 一次 draw call 只能绑定一套材质状态，因此必须按材质拆分。每个 Section 对应一个 `aiMesh`，持有自己的顶点、索引和 `MaterialIndex`。这与 UE 的 `FStaticMeshSection` 是同一个概念。

**切线与 TBN**：法线贴图存的是**切线空间**的法线扰动，而非世界空间。这样同一张贴图可以贴到任意朝向的表面上。要把它转到世界空间，需要构造 TBN 矩阵——Tangent、Bitangent、Normal 三个正交轴。其中 Tangent 必须与 UV 的 U 方向对齐，因此依赖 UV 布局，只能由导入时计算。

本项目顶点只存 Tangent 不存 Bitangent，在 shader 里用 `cross(n, t)` 现场算（`model.frag` 的 `GetMaterialNormal`），同时做 Gram-Schmidt 正交化。这省了 12 字节/顶点，代价是丢失了手性信息（镜像 UV 的模型可能出问题）。

**顶点格式**（`FStaticMeshVertex`，56 字节）：Position、Normal、Tangent、TexCoord、Color。

**材质与颜色空间**：`FMaterial` 的每个贴图槽携带 `ColorSpace` 语义——BaseColor 与 Emissive 是 sRGB，Normal / Metallic / Roughness / AO 是 Linear。这个标记一路传到 `RHITextureDesc::srgb`。搞错的表现是法线贴图被 sRGB 解码后方向全歪，或 Roughness 数值被非线性扭曲。

## 第 6 站：游戏侧与渲染侧的分离 ★

**前置**：第 1 站、第 5 站

这是本项目最重要的架构思想，也是它区别于「教程级渲染器」的地方。

### 要回答的问题

- 为什么不让 `MeshComponent` 直接持有 VertexBuffer 并自己画自己？
- SceneProxy 是什么，为什么要有这层镜像？
- 为什么资源准备发生在「注册时」而不是「渲染时」？



### 原理要点

**问题的根源**：游戏逻辑和渲染的关注点、生命周期、乃至线程都不同。游戏侧关心「这个敌人在哪、血量多少」，渲染侧关心「哪些三角形用哪个 pipeline 画」。如果让组件直接持有 GPU 资源：

- 游戏逻辑代码里混进了图形 API 细节
- 无法引入渲染线程，因为渲染要读的数据随时可能被游戏逻辑改写
- 单元测试游戏逻辑必须先初始化整个图形栈

**UE 的解法是 SceneProxy 模式**，本项目照搬：游戏侧的每个 `PrimitiveComponent` 在渲染侧有一个镜像 `FPrimitiveSceneProxy`。两者通过稳定 ID 关联，通过显式接口同步。

```text
游戏侧                        边界                   渲染侧
────────                    ────────               ────────
PrimitiveComponent  ──CreateSceneProxy()──▶  FPrimitiveSceneProxy
      │                                              │
      │ MarkRenderStateDirty()                       │
      ▼                                              ▼
World::SyncToScene()  ──IRenderScene::Update──▶  FScene
                          （每帧唯一通道）      └─ FPrimitiveSceneInfo
```

**几个关键设计点**：

`IRenderScene` **接口反转依赖。** `World` 模块不依赖 `Renderer` 模块，只依赖 `RenderCore` 中定义的接口。`FScene` 实现这个接口。这样 `World` 可以在没有渲染器的情况下编译和测试。

**脏标记 + 延迟同步。** 组件变换改变时只置一个 bool，不立刻做任何事。帧末统一扫描并同步。好处是同一帧内多次修改只同步一次，且同步点集中可控。注意本项目的脏标记需要**显式调用** `MarkRenderStateDirty()`，改了 Transform 不会自动脏——这是简化实现，忘记调用的表现是物体在画面上不动。

**资源准备在注册阶段。** `FScene::AddPrimitive` 时就通过 `FRenderResourceManager` 完成 GPU 上传和 pipeline 预热，而不是等到第一次渲染。这避免了第一帧的卡顿尖峰（俗称 shader compilation stutter 的一种形式）。

**RenderData 是资产级共享的。** `FStaticMeshRenderData` 按 `StaticMesh`* 缓存，同一个模型放 100 个实例只上传一次顶点数据，100 个 SceneProxy 共享引用。SceneProxy 只持有实例级状态（世界变换）。这是「资产 vs 实例」的分离，也是实例化渲染的前提。

**当前的简化之处**（学习时要知道边界在哪）：`SceneComponent::GetWorldMatrix()` 直接返回本地 Transform，**没有实现父子层级**。完整实现应该是 `World = Parent.World * Local` 递归。代码注释里明确标注了这一点。

## 第 7 站：RHI 抽象层

**前置**：第 6 站

### 要回答的问题

- 为什么需要一层图形 API 抽象？直接写 OpenGL 不行吗？
- OpenGL 和 Vulkan 差异那么大，怎么统一？
- BindGroup / PipelineLayout 这些概念是从哪来的？



### 原理要点

**抽象层要解决的不只是「支持多个 API」**，更重要的是**倒逼上层代码采用现代 API 的思维模型**。OpenGL 是隐式的全局状态机，写惯了会形成「随时改状态、驱动帮我管一切」的习惯；Vulkan 要求显式声明一切。如果先按 OpenGL 风格写好，再想接 Vulkan，基本等于重写。

本项目的 RHI **按 Vulkan/D3D12 的模型设计，让 OpenGL 去适配**，而不是反过来。这是关键决策。

**核心抽象及其对应关系**：


| RHI 类型               | Vulkan 对应               | 作用             |
| -------------------- | ----------------------- | -------------- |
| `RHIDevice`          | `VkDevice`              | 资源工厂 + 帧生命周期   |
| `RHICommandBuffer`   | `VkCommandBuffer`       | 命令录制           |
| `RHIPipeline`        | `VkPipeline`            | 完整的渲染状态对象（PSO） |
| `RHIPipelineLayout`  | `VkPipelineLayout`      | 声明接受哪些资源组      |
| `RHIBindGroupLayout` | `VkDescriptorSetLayout` | 资源组的**形状**     |
| `RHIBindGroup`       | `VkDescriptorSet`       | 资源组的**内容**     |
| `RHIRenderTarget`    | Framebuffer / MRT       | 离屏渲染目标         |


**Layout 与 Group 分离**为什么重要：Layout 描述「这个槽位接受一个 uniform buffer，那个槽位接受一张贴图」，是编译期就能确定的形状；Group 是填了具体资源的实例。Pipeline 创建时校验 Layout，运行时只切换 Group。这让 GPU 驱动能提前做验证和优化。

**帧生命周期**：`BeginFrame` 返回 `RHIFrameContext`（含 command buffer、frameIndex、swapChainImageIndex），`EndFrame` 提交并呈现。这个上下文**只在配对之间有效**。RenderPath 不自己 Begin/End command buffer，边界由 Device 统一持有——这样 Vulkan 的 acquire/submit/present 时序能被完整封装。

**Transient Uniform Ring + Dynamic Offset**：这是现代 per-draw uniform 的标准做法，值得单独理解。朴素做法是每个 draw 创建一个小 UBO，但创建/销毁 buffer 是重操作。Ring 方案是：分配一个大 buffer，每帧从头开始按 offset 线性分配，绑定时通过 dynamic offset 指定用哪一段。BindGroup 本身保持不变，只有 offset 变化。OpenGL 用 `glBindBufferRange` 实现，Vulkan 用 `vkCmdBindDescriptorSets` 的 dynamicOffsets 参数。

`RHIBackendTraits` **处理后端差异**：与其到处写 `#ifdef`，不如让后端声明自己的特性，上层查询后适配：


| Trait                         | 含义                         |
| ----------------------------- | -------------------------- |
| `bNativeNDCDepthZeroToOne`    | 原生深度范围是否 `[0,1]`           |
| `bNativeNDCYAxisUp`           | NDC 的 Y 轴朝上还是朝下（Vulkan 朝下） |
| `bNativeTextureOriginTopLeft` | 纹理原点位置                     |
| `bRTSampleRequiresFlipY`      | 采样 RT 时是否需要翻转 V            |
| `bSupportsSceneRendering`     | 能否执行真实绘制                   |
| `bSupportsFullSceneRendering` | 能否跑完整 Forward/Deferred/PBR |


最后两个是**能力门控**的巧妙用法：Vulkan 阶段 B 设为 `true/false`，于是能进入真实的 Renderer 代码路径做垂直切片验证，但不假装自己支持完整 PBR。这避免了「要么全实现要么只能清屏」的二选一困境。

**共享 GLSL 的跨后端处理**：一套 shader 源码，通过宏适配两个后端：

```glsl
#if defined(TE_RHI_VULKAN)
    #define TE_UNIFORM_BINDING(g,b) layout(std140, set = g, binding = b)
#else
    #define TE_UNIFORM_BINDING(g,b) layout(std140, binding = b)   // OpenGL 无 set 概念
#endif
```

**当前的薄弱点**：binding 信息在 shader 宏和 C++ 的 `RendererBindings` 里各写了一份，靠人工保持一致，没有反射或代码生成。这是已知的结构性问题，见踩坑记录第二部分第 5 条。

## 第 8 站：一次 Draw 的完整数据流

**前置**：第 6 站、第 7 站

这一站不引入新概念，而是把前面所有内容串成一条线。理解了这条线，就理解了整个渲染器。

### 要回答的问题

从「场景里有个立方体」到「屏幕上有像素」，中间到底经过了什么？

### 完整链路

```text
① 资产层
   StaticMesh（CPU 顶点/索引/材质槽）
        │
② 注册期（FScene::AddPrimitive）
   ├─ GetOrCreateStaticMeshRenderData  → 上传顶点/索引到 GPU（资产级缓存）
   ├─ EnsurePipeline(PipelineKey)      → 编译 shader、创建 PSO（共享）
   ├─ EnsureStaticMeshMaterialTextures → 上传贴图，建纹理 BindGroup
   └─ EnsureEnvironmentResources       → 生成 IBL 资源（全局一次）
        │
③ 每帧游戏侧
   Actor 移动 → MarkRenderStateDirty → World::SyncToScene → Proxy.WorldMatrix 更新
        │
④ 每帧收集（FMeshPassProcessor）
   遍历 FScene 的 Primitive → 每个 Section 产出一条 FMeshDrawCommand
   命令里存的是 PipelineKey（不是 Pipeline 指针）、VB/IB、MaterialIndex、WorldMatrix
        │
⑤ 排序
   按 Pass → MaterialDomain → VertexFactory → VB 指针 → IB 指针
   目的：让相同状态的 draw 相邻，减少绑定切换
        │
⑥ 提交（逐 command）
   ├─ PipelineKey → 解析出真实 Pipeline → BindPipeline
   ├─ 计算 MVP / Model / NormalMatrix → 写入 transient ring → SetBindGroup(group 1, offset)
   ├─ 材质因子 → transient ring → SetBindGroup(group 3, offset)
   ├─ 材质贴图 BindGroup → SetBindGroup(group 2)
   ├─ 光源数据 → transient ring → SetBindGroup(group 0, offset)
   ├─ IBL 资源 BindGroup → SetBindGroup(group 4)
   ├─ BindVertexBuffer / BindIndexBuffer
   └─ DrawIndexed(FirstIndex, IndexCount)
        │
⑦ 后端执行 → GPU
```



### 需要理解的设计点

**为什么 DrawCommand 里存 PipelineKey 而不是 Pipeline 指针？** 收集阶段和提交阶段解耦。收集时只描述「需要什么样的 pipeline」（结构化的 `{Pass, MaterialDomain, VertexFactory}`），提交时才查表拿到真实对象。这让收集阶段可以并行化，也让 pipeline 的创建时机可控。

**为什么要排序？** 每次 `BindPipeline` 和 `BindVertexBuffer` 都有开销，GPU 状态切换尤其贵。把相同状态的 draw 排在一起，就能跳过重复绑定。排序键的层级顺序反映了各类状态切换的代价：pipeline 最贵所以排最外层。

**BindGroup 的分组方案**反映了**更新频率**：


| Group | 内容                                 | 更新频率    |
| ----- | ---------------------------------- | ------- |
| 0     | LightBlock                         | 每帧一次    |
| 1     | PassBlock（Object / Deferred / Sky） | 每 draw  |
| 2     | 材质贴图 / GBuffer 贴图                  | 每材质     |
| 3     | MaterialBlock（因子）                  | 每 draw  |
| 4     | Environment（IBL）                   | 全局，几乎不变 |


按更新频率分组是 descriptor set 设计的标准原则：变化慢的放低 group，变化快的放高 group，这样切换 group 时不必重新绑定不变的部分。

## 第 9 站：PBR 直接光照 ★

**前置**：第 2 站、第 8 站

### 要回答的问题

- PBR 里的「物理」具体指什么？
- D、G、F 三项各自在描述什么？
- metallic 和 roughness 到底控制什么？



### 原理要点

**PBR 的核心是能量守恒与微表面理论**。它不是某个具体公式，而是一套约束：反射出去的能量不能超过入射能量，材质参数应该有物理意义而非艺术家随手调的魔数。

**微表面理论**：把粗糙表面建模为大量微小的完美镜面。宏观上看到的漫散射，实际是无数微镜面朝向各异造成的。这个模型让 roughness 有了明确定义——微表面朝向的统计分布宽度。

**Cook-Torrance 镜面项**：

```text
f_specular = D · G · F / (4 · (n·v) · (n·l))
```

三项分工：

**D（法线分布函数，GGX/Trowbridge-Reitz）** 回答「有多少比例的微表面法线正好朝向半程向量 h」。这决定了高光的形状：roughness 小则分布集中，高光小而亮；roughness 大则分散，高光大而暗。GGX 相比早期的 Beckmann 有更长的拖尾（long tail），高光边缘过渡更自然，这是它成为业界标准的原因。

```52:60:Content/Shaders/OpenGL/model.frag
float DistributionGGX(vec3 n, vec3 h, float roughness)
{
    float a = roughness * roughness;
    float a2 = a * a;
    float nDotH = max(dot(n, h), 0.0);
    float nDotH2 = nDotH * nDotH;
    float denom = (nDotH2 * (a2 - 1.0) + 1.0);
    return a2 / max(PI * denom * denom, 0.0001);
}
```

注意 `a = roughness * roughness`。这个平方是 Disney 提出的**感知线性化**：直接用 roughness 的话，视觉上从 0.1 到 0.2 的变化远大于从 0.8 到 0.9，平方后调节手感更均匀。这是「艺术家友好」的参数化，不是物理需求。

**G（几何遮蔽函数，Smith + Schlick-GGX）** 回答「有多少微表面被相邻微表面挡住了」。分为遮蔽（shadowing，光进不来）和阴影（masking，光出不去），Smith 方法把两者拆成独立的两次求值再相乘。粗糙表面在掠射角下遮蔽严重，没有 G 项的话边缘会异常发亮。

**F（菲涅尔，Schlick 近似）** 回答「有多少比例的光被反射而非折射」。它随入射角变化：正视时反射少，掠射时几乎全反射（这就是为什么平视水面能看到倒影，俯视能看到水底）。Schlick 近似用 `F0 + (1-F0)(1-cosθ)⁵` 拟合，误差很小但快得多。

**metallic 工作流的本质**是用一个参数在两类材质间插值：

```text
F0 = mix(vec3(0.04), baseColor, metallic)
kD = (1 - F) * (1 - metallic)
```

- **电介质**（塑料、木头、皮肤）：F0 ≈ 0.04 且无色，有漫反射，baseColor 就是漫反射颜色
- **金属**：F0 高且有颜色，**没有漫反射**（自由电子吸收了折射光），baseColor 实际是 F0

所以 `metallic` 不是「金属感」滑条，而是二元开关的连续化——中间值物理上不存在真实材质，只用于表现锈蚀等混合表面。

**能量守恒的体现**是 `kD = (1 - kS)`：被镜面反射走的能量不能再参与漫反射。

**点光衰减**：本项目用 `clamp(1 - d/radius, 0, 1)²`，这是**非物理**的。真实的平方反比衰减 `1/d²` 没有有限作用范围，会一直延伸到无穷远，不利于剔除。带 radius 的窗函数是实时渲染的常见妥协，UE 和 Unity 也用类似方案。

## 第 10 站：IBL 环境光照

**前置**：第 9 站

这一站有**独立的完整文档**：[IBL 环境光照原理与实现](./IBL环境光照原理与实现.md)。

### 简要脉络

直接光只能表达少数几个光源，但现实中光来自四面八方。IBL 用一张 HDR 全景图记录环境每个方向的辐亮度，把环境当成一个包裹场景的巨大光源。

核心困难是逐像素做半球积分不可行，因此把积分中与运行时无关的部分预计算成贴图：

- **Diffuse**：Lambert BRDF 是常数可提出积分，剩下的辐照度只依赖法线，存成 irradiance cubemap
- **Specular**：用 split-sum 近似拆成「预滤波环境图」×「BRDF LUT」两个可独立预计算的积分

本项目在 CPU 上启动期生成这三张贴图。专题文档中详细推导了每个公式、对应到具体代码行，并记录了三处与标准实现的偏差（diffuse 亮 π 倍、prefilter 是占位实现、tonemap 不一致）。

## 第 11 站：延迟渲染

**前置**：第 8 站、第 9 站

### 要回答的问题

- Forward 和 Deferred 的本质区别是什么？
- GBuffer 里应该存什么，不应该存什么？
- 为什么可以从深度反推世界坐标？



### 原理要点

**Forward 的瓶颈**：每个物体的每个像素都要跑一遍完整的光照循环。复杂度是 `O(物体数 × 光源数)`，且被遮挡的像素也白算了（overdraw）。光源一多就崩。

**Deferred 的想法**：把「几何信息收集」和「光照计算」拆成两个 pass。

```text
Pass 1（GBuffer）：光栅化所有几何，把 albedo/normal/材质参数写进多张 RT，不算光照
Pass 2（Lighting）：一个全屏三角形，逐像素读 GBuffer，算光照
```

复杂度变成 `O(物体数 + 屏幕像素 × 光源数)`，且只有最终可见的像素才参与光照。

代价也很明确：**带宽换计算**。GBuffer 的写入和读取消耗大量显存带宽；**不支持 MSAA**（因为光照发生在解析之后）；**不支持半透明**（半透明需要混合多层，GBuffer 只能存一层）。所以现代引擎通常是 Deferred 处理不透明物体 + Forward 处理半透明的混合方案。

**本项目的 GBuffer 布局**：


| RT    | 格式        | 内容                                    |
| ----- | --------- | ------------------------------------- |
| 0     | RGBA8     | Albedo                                |
| 1     | RGBA8     | 世界法线，编码为 `n * 0.5 + 0.5`              |
| 2     | RGBA32F   | 世界坐标（**仅供 debug 对照**）                 |
| 3     | RGBA8     | metallic, roughness, ao, emissiveLuma |
| Depth | D32_Float | 深度                                    |


法线的 `*0.5+0.5` 编码是因为 RGBA8 只能存 `[0,1]` 而法线分量在 `[-1,1]`。更省的做法是八面体编码（octahedral）用两个通道存法线，本项目暂未使用。

**从深度重建世界坐标**是 Deferred 的关键技巧。RT2 存世界坐标看似直接，但每像素 16 字节的带宽代价很高，而这个信息其实是**冗余的**——深度缓冲已经隐含了它：

```text
1. 屏幕 UV → NDC XY：uv * 2 - 1
2. 深度值 → NDC Z（是否需要 *2-1 取决于后端 NDC 深度范围）
3. inverse(ViewProjection) * vec4(ndcXYZ, 1)
4. 齐次除法：xyz / w
```

本项目**正式光照走重建路径**，RT2 只保留给 `F6`（显示存储的世界坐标）和 `F8`（显示两者的误差热力图）两个调试视图。`F8` 这个误差视图是很好的教学工具：它把「重建到底准不准」这个抽象问题变成了可视化的颜色分级。

**GBuffer 必须用 Nearest 采样**。项目里踩过这个坑：Lighting Pass 一开始复用了默认的 Linear sampler，结果法线和深度被线性插值，斜视表面时异常变亮。GBuffer 存的是结构化数据不是颜色，相邻像素的法线插值出来的结果没有任何物理意义。

**资源状态转换**：GBuffer 在 Pass 1 是渲染目标，Pass 2 是被采样的纹理，中间必须显式切换状态。Vulkan 里这是真实的 image layout transition，OpenGL 里退化为 `glMemoryBarrier`。RHI 保留了 Vulkan 语义，让上层代码跨后端一致。

## 第 12 站：深度精度与 Reversed-Z

**前置**：第 2 站、第 11 站

### 要回答的问题

- 为什么远处物体会出现深度冲突（z-fighting）？
- 把近远平面反过来为什么能改善精度？
- 改成 Reversed-Z 需要同时改哪几处？



### 原理要点

**问题的根源是两个非线性叠加**。

透视投影后，深度值与真实距离的关系是 `1/z` 形式的：近处一小段距离占用大量深度值范围，远处很长一段距离才占用一点点。这是透视除法的必然结果。

而浮点数本身的精度分布也是非均匀的：接近 0 的地方精度极高（指数可以很小），接近 1 的地方精度低（尾数位固定但数值大）。

传统约定是 near→0、far→1。于是两个非线性**方向相同、叠加放大**：远处既因透视而深度值密集，又因浮点在 1 附近而精度低。结果就是远处深度冲突。

**Reversed-Z 的解法**是把深度反过来：near→1、far→0。这样远处的深度值落在浮点精度最高的 0 附近，两个非线性**相互抵消**。这是几乎零成本的巨大改善——只要用浮点深度缓冲，就没有理由不用 Reversed-Z。

**需要同步修改的地方**（漏改任何一处都会出问题）：


| 项目     | 传统     | Reversed-Z             |
| ------ | ------ | ---------------------- |
| 深度清除值  | 1.0    | **0.0**                |
| 深度比较函数 | `Less` | `Greater`              |
| 投影矩阵   | 标准     | 深度行取反平移                |
| 深度缓冲格式 | 可用 D24 | **必须浮点（D32F）**，整数格式会失效 |


**注意最后一条**：Reversed-Z 依赖浮点数在 0 附近的高精度。用固定点的 D24 格式的话，精度是均匀分布的，反转不但没有收益，反而因为透视的非线性而变差。

本项目通过 `RendererDepthConvention` 统一管理这套约定，投影转换由 `Matrix4::ReverseZProjectionZO` 完成（本质是左乘一个把 `z` 变成 `w - z` 的矩阵）。**CPU 侧的 Frustum 剔除仍使用正向 ZO**——剔除是纯 CPU 几何计算，不涉及深度缓冲精度，没必要跟着反转。

**调试提示**：`F7` 显示的深度视图是未线性化的 Reversed-Z 原始值，所以近处亮、远处暗。它适合检查深度覆盖和方向，但不能当作线性距离读。

## 第 13 站：Vulkan 后端

**前置**：第 7 站

### 要回答的问题

- Vulkan 相比 OpenGL 多了哪些必须手工管理的东西？
- 什么是帧同步，为什么需要两套索引？
- 为什么这个后端是分阶段实现的？



### 原理要点

**Vulkan 的设计哲学是「把驱动做的事交给应用做」**。OpenGL 驱动帮你管理同步、内存、状态验证，代价是不可预测的开销和难以并行。Vulkan 把这些全部显式化。

必须手工管理的清单：


| 内容         | OpenGL            | Vulkan                                  |
| ---------- | ----------------- | --------------------------------------- |
| 交换链        | 驱动隐藏              | 手工创建、手工重建                               |
| CPU/GPU 同步 | 驱动隐藏              | Fence 显式等待                              |
| GPU 内部同步   | 驱动隐藏              | Semaphore 显式串联                          |
| 图像布局       | 无此概念              | 每次用途变化都要 barrier                        |
| 内存分配       | 驱动隐藏              | 手工选 memory type、手工分配                    |
| 上传数据       | `glTexImage2D` 一步 | staging buffer + copy command + barrier |
| Shader     | 运行时编译 GLSL        | 预编译为 SPIR-V                             |


**帧同步与两套索引**是最容易搞混的地方：

- `frameIndex`**（frame slot）**：CPU 侧的资源轮转索引。为了让 CPU 能提前录制下一帧而不等 GPU，需要多份 command buffer、fence、semaphore。通常 2~3 份。
- `swapChainImageIndex`：`vkAcquireNextImageKHR` 返回的、本次要渲染到哪张交换链图像。**它的顺序不保证与 frameIndex 对应**。

因此两类资源要分别管理：command pool、command buffer、image-available semaphore、in-flight fence 按 frame slot；render-finished semaphore、深度图像按交换链图像。此外还需要 `m_ImagesInFlight` 映射，防止同一张交换链图像上一次的提交还没完成就被重新录制。

**一帧的同步链条**：

```text
等待 frame slot 的 fence（确保这套资源 GPU 用完了）
  → vkAcquireNextImageKHR，signal imageAvailable semaphore
  → 录制 command buffer
  → vkQueueSubmit：wait imageAvailable，signal renderFinished，signal fence
  → vkQueuePresentKHR：wait renderFinished
```

**交换链重建**：窗口 resize、VSync 变化、或返回 `VK_ERROR_OUT_OF_DATE_KHR` / `VK_SUBOPTIMAL_KHR` 时必须重建。有个容易踩的坑：最小化时 surface extent 可能在你检查尺寸**之后**才异步变成零，所以创建函数还要二次检查最终 extent。

**Dynamic Rendering**（Vulkan 1.3）：省去了传统的 `VkRenderPass` 和 `VkFramebuffer` 对象，直接 `vkCmdBeginRendering` 指定附件。大幅简化了代码，代价是失去了 tile-based GPU 上的一些优化提示。本项目直接用它。

**分阶段实施的意义**：Vulkan 后端不可能一次写完就跑通完整场景。项目的做法是用 `bSupportsFullSceneRendering = false` 门控，让 Vulkan 进入真实的 `FSceneRenderer` 但走内部的 `FStaticMeshValidationRenderPath`——一个渲染旋转立方体的最小垂直切片，验证 buffer / texture / descriptor / pipeline / dynamic rendering 的完整链路，但不碰 TextureCube、MRT、IBL 这些还没实现的能力。

这是很值得学习的工程方法：**用能力门控代替「全有或全无」**。否则要么被迫一次实现所有特性，要么只能停留在清屏阶段无法验证真实绘制。

**当前明确未实现**：离屏 RenderTarget / MRT、TextureCube、多 mip、完整 Forward/Deferred/PBR、fence retirement queue、显存子分配器、异步批量上传。阶段 B 仍是每资源独立分配 + 启动期同步上传。
